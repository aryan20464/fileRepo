## Agenda

To discuss the timeline for onboarding the ISD Department into the CI/CD automation process for IDEA applications, enabling them to review and validate false-positive observations identified in Fortify SAST scan reports during application source code scanning.

## Background

The DevSecOps platform, managed by the PE-III Department, is the Bank's automated application build and deployment platform. It automates the application build and deployment process across target environments, thereby reducing manual intervention by developers.

As part of the CI/CD pipeline, the first stage involves static application security testing using the Fortify SAST tool. Applications are permitted to proceed to the build and subsequent deployment stages only after the Fortify scan is cleared without blocking observations.

## Discussion Points

1. The ISD Department currently provides security clearance for IDEA applications after reviewing and validating security observations identified during the application security assessment process. The review outcome is recorded and communicated through the EPM tool.

2. During Fortify SAST scanning on the DevSecOps platform, certain observations are being reported that have either:

   * already been reviewed and accepted by ISD during the security assessment process, or
   * are identified by the scanning tool due to the absence of complete application context, resulting in false-positive findings.

   For example, user authentication and authorization are validated at the initial stage of request processing. Only authenticated and authorized users are permitted to access application functionalities based on the implemented access control mechanism. However, in some cases, the Fortify tool is unable to accurately interpret this implementation and reports observations such as "User Not Validated," even though the required security controls are in place. Such observations are treated as false positives.

3. The PE-III DevSecOps Team informed that the current DevSecOps platform does not provide a mechanism to validate or mark Fortify observations as false positives. Discussions are currently underway with the ISD Department to onboard them into the CI/CD workflow so that they can review and provide decisions on such observations.

4. Until the above process is implemented, the DevSecOps Team has advised that application teams should communicate all observations identified as false positives to the DevSecOps Team through email. This process will be followed for deployments across all environments, including UAT and Production.

5. It was agreed that the above interim procedure will continue to be followed until a formal process for validating false-positive observations is established and communicated by the concerned departments.
